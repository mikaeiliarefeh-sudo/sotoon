## ۱. صورت‌حساب و شمارش توکن (cache)

**چرا مهم است:** یک مشتری (پاتوق) گفته ما توکن را بیشتر از واقعیت می‌شماریم. او از **Bifrost** (gateway) و Bedrock استفاده می‌کرد. ⚠️ *روشن نیست Sotoon در Bifrost provider بوده یا مقایسه با Bedrock بوده؛ ابزار کدنویسی (مثل Claude Code) در کار نبوده. باید از پاتوق پرسید: اختلاف بین چه دو عددی بود، و `usage` خام یک درخواست مشخص از هر دو سمت.* اگر هزینه برای توکن‌های cache گران‌تر از واقع حساب شود، از مشتری بیشتر می‌گیریم.

**آنچه می‌دانیم:**
- تعداد توکن مصرفی هر مشتری را از **LiteLLM** می‌خوانیم.
- LiteLLM برای هر مشتری یک **هزینه** هم نگه می‌دارد.
- در داشبورد مشتری، **تعداد توکن** نمایش داده می‌شود (و هزینه).
- LiteLLM قیمت cache را جدا حساب می‌کند **اگر** در تعریف مدل `cache_read_input_token_cost` و `cache_creation_input_token_cost` تنظیم شده باشد. اسکریپت `fetch_openrouter_models.py` این‌ها را فقط وقتی تنظیم می‌کند که OpenRouter قیمت `input_cache_read` / `input_cache_write` داده باشد (و ۱۵٪ مارجین هم روی آن‌ها اعمال می‌شود).

**روشن‌شده:** واحد فاکتور ریال است و بر اساس نرخ دلار روز ۲۳ام محاسبه می‌شود.

**آنچه نمی‌دانیم (باید روشن شود):**
1. هزینه‌ای که مشتری در پنل می‌بیند از کجا می‌آید؟
   - **الف)** مستقیم از هزینه‌ی ثبت‌شده در LiteLLM ← مشکلی نیست (اگر cache درست تنظیم شده باشد).
   - **ب)** از فرمول خودمان: `قیمت هر میلیون توکن × تعداد توکن` ← اگر تعداد توکن شامل توکن‌های cache باشد، همه با قیمت کامل حساب می‌شوند و **بیش‌حساب** است.
2. «تعداد توکن» پنل، توکن‌های cache را هم داخل ورودی می‌شمارد؟

**فرضیه‌ها (تأییدنشده، از روی کد ندیده‌ام):**
- **شمارش:** LiteLLM `prompt_tokens` را معمولاً با جمع توکن‌های ورودی + cache می‌سازد. در کنسول خود Anthropic/Bedrock، `input_tokens` معمولاً جدا از توکن‌های cache نمایش داده می‌شود. پس مشتری عدد کمتری در کنسول آن‌ها می‌بیند و ما بیشتر. Claude Code و ابزارهای مشابه خیلی از cache استفاده می‌کنند، پس اختلاف بزرگ می‌شود.
- **مبلغ:** برای مدل‌هایی که قیمت cache در تعریفشان تنظیم نشده (یا مدل‌های OpenAI مستقیم که از اسکریپت OpenRouter نمی‌آیند)، توکن cache با قیمت کامل ورودی حساب می‌شود.

**راه تحقیق (سه‌طرفه):** برای یک مشتری و یک روز، سه عدد را کنار هم بگذارید:

| منبع | چه چیزی |
|---|---|
| ۱. لاگ خرج LiteLLM (Spend Logs) | `prompt_tokens`، توکن cache، `completion_tokens`، `spend` به‌ازای هر درخواست |
| ۲. پنل مشتری | همان روز: توکن و هزینه |
| ۳. محاسبه‌ی دستی | `(ورودی غیر cache × قیمت ورودی) + (خوانش cache × قیمت cache read) + (نوشتن cache × قیمت cache write) + (خروجی × قیمت خروجی)` با قیمت ما |

- اگر ۱ ≠ ۲: پنل خودش جدا حساب می‌کند.
- اگر ۱ ≠ ۳: LiteLLM قیمت cache را برای آن مدل ندارد یا غلط دارد.
- توکن پنل را با کنسول خود Anthropic/Bedrock برای همان بازه مقایسه کنید.
- مشتری پاتوق: با خودش هماهنگ کنید که یک روز مشخص و مدل مشخص را بررسی کنیم.

**آزمایش سریع (۱۰ دقیقه، با `curl`):** دو بار یک درخواست بلند یکسان به یک مدل OpenAI بفرستید و در پاسخ ببینید `cached_tokens` و هدر `x-litellm-response-cost` بار دوم کمتر می‌شود یا نه:

```bash
LONG=$(yes "Sotoon cache test sentence number one." | head -n 400 | tr '\n' ' ')
for i in 1 2; do
  curl -s -D /tmp/h$i.txt -o /tmp/b$i.json https://api.intelligence.sotoon.ir/inference/v1/chat/completions \
    -H "Authorization: Bearer $SOTOON_API_KEY" -H "Content-Type: application/json" \
    -d "{\"model\":\"openai/gpt-5-nano\",\"max_tokens\":200,\"messages\":[{\"role\":\"user\",\"content\":\"$LONG Say hi.\"}]}"
  echo "--- call $i"; grep -i 'x-litellm-response-cost' /tmp/h$i.txt
  python3 -c "import json,sys;print(json.load(open(sys.argv[1]))['usage'])" /tmp/b$i.json
  sleep 5
done
```

- بار دوم باید `prompt_tokens_details.cached_tokens` بزرگ‌تر از صفر داشته باشد (cache خودکار OpenAI).
- اگر هزینه‌ی بار دوم در هدر **کمتر** شد، LiteLLM تخفیف cache را اعمال می‌کند. اگر **برابر** ماند، تخفیف اعمال نمی‌شود.
- بعد در پنل مشتری ببینید توکن همان دو درخواست چقدر اضافه شده و هزینه چقدر.

**نتیجه‌ی تست ۱ (Claude Opus 4.6، `/v1/messages`، با `cache_control`، دو بار پشت‌سرهم):**
- `usage` فقط `input_tokens: 13512` در هر دو بار؛ هیچ فیلد `cache_creation_input_tokens` / `cache_read_input_tokens` برنگشت.
- هزینه‌ی اصلی: call 1 = ۰.۰۷۸۱۵۴ و call 2 = ۰.۰۷۸۱۲۵ دلار ← تقریباً برابر. با فرض قیمت ورودی/خروجی $5/$25 و ۱۵٪ مارجین، دقیقاً مطابق محاسبه‌ی «کل ورودی با قیمت کامل» است. (فرض قیمت از منطبق شدن عددها نتیجه شد، نه از جدول رسمی.)
- مارجین در قیمت مدل جاسازی شده (`margin-amount` = ۰).
- یعنی cache اعمال نشد یا گزارش نشد. یا `cache_control` گم می‌شود (مشتری تخفیف را از دست می‌دهد)، یا cache بالادست ساخته می‌شود و ما تخفیف را نمی‌رسانیم (بیش‌حساب).
- شناسه‌های OpenRouter برای بررسی بک‌اند: `gen-1790939116-UZQDdLyr8xiovfA40RVF` و `gen-1790939131-EW1OwBzFH44dN5xMUTzK` ← در Activity حساب OpenRouter ببینند cache_read/تخفیف ثبت شده یا نه.

**نتیجه‌ی تست ۲ (همان مدل، `/v1/chat/completions`، با `cache_control` در content، ~۵ دقیقه بعد از تست ۱):**
- `usage.prompt_tokens_details.cached_tokens: 13503` در **هر دو** call (حتی call 1 که انتظار نوشتن cache داشتیم ← یعنی cache از تست ۱ (`/messages`) مانده بود و احتمالاً آن درخواست‌ها هم cache ساخته/خوانده‌اند، ولی گزارش نشد).
- `usage.cost: 0.0071965` (هزینه‌ی بالادست OpenRouter، بدون مارجین ما)؛ `cost_details`: prompt 0.0067965 (۱۳۵۰۳ توکن cache با ≈۰.۵$/M + ۹ توکن عادی) + completion 0.0004.
- مقایسه: هزینه‌ی ثبت‌شده‌ی `/messages` = ۰.۰۷۸ در برابر هزینه‌ی بالادست ≈ ۰.۰۰۷ ← حدود ۹ تا ۱۰ برابر، **اگر** هزینه‌ی ما همان ۰.۰۷۸ باشد (تأییدنشده).
- provider در پاسخ: `Claude Platform on AWS`.
- هدر هزینه‌ی LiteLLM در خروجی این مسیر چاپ نشد (فیلتر ناقص بود) ← باید با `grep -i x-litellm` دوباره دید.
- ⚠️ *هنوز انجام نشده:* تست با salt تازه برای هر دو مسیر (با همه‌ی هدرهای LiteLLM)، مقایسه‌ی عدد پنل قبل/بعد، تست OpenAI (`gpt-5-nano`)، بررسی Activity در OpenRouter.
- **پیام پیشنهادی به بک‌اند:** «در `/v1/messages` فیلدهای cache در `usage` نیست و هزینه با قیمت کامل ورودی ثبت می‌شود؛ در `/v1/chat/completions` همان مدل `cached_tokens` را درست برمی‌گرداند و هزینه‌ی بالادست ≈ یک‌دهم است (نمونه: ۱۳٬۵۰۰ توکن ورودی، Claude Opus 4.6: ۰.۰۷۸ دلار در `/messages` در برابر ۰.۰۰۷ دلار در `/chat/completions`).»

**نتیجه‌ی تست ۳ (salt تازه برای هر مسیر، همه‌ی هدرهای LiteLLM):**

| درخواست | `usage` | هزینه‌ی ثبت‌شده (LiteLLM) | هزینه‌ی واقعی بالادست |
|---|---|---|---|
| chat call 1 | `cache_write_tokens: 13508` | 0.084845 | 0.084845 |
| chat call 2 | `cached_tokens: 13508` | 0.007199 | 0.007199 |
| messages call 1 | بدون فیلد cache | 0.07818275 | ≈0.0848 (نوشتن cache) |
| messages call 2 | بدون فیلد cache | 0.078154 | ≈0.0072 (خواندن cache) |

- **مشکل A (`/v1/messages`):** فیلدهای cache در `usage` نیست و LiteLLM کل ورودی را با قیمت عادی (+۱۵٪) حساب می‌کند ← نوشتن cache ≈۸٪ کم‌حساب، خواندن cache ≈۱۱ برابر بیش‌حساب. Claude Code از این مسیر می‌آید و عمدتاً cache می‌خواند ← بیش‌حساب جدی.
- **مشکل B (`/v1/chat/completions`):** `x-litellm-response-cost` دقیقاً برابر `usage.cost` اوپن‌روتر است ← cache درست حساب می‌شود ولی **مارجین ۱۵٪ اعمال نمی‌شود** (⚠️ از تطابق عددها نتیجه شد؛ بک‌اند تأیید کند).
- هدر `x-litellm-key-spend` با تأخیر به‌روز می‌شود؛ مجموع انتظار: ≈0.2484 دلار برای چهار درخواست اگر پنل از LiteLLM بخواند، ≈0.313 اگر «قیمت × توکن» باشد (تأییدنشده؛ باید عدد پنل قبل/بعد دید).
- شناسه‌های OpenRouter: `gen-1790940088-5c0VJ0phUBizdBejIrZA`، `gen-1790940112-yHPh7YxNz8wdVX4bd85t`، `gen-1790940142-srqRLB41b0ikc6PphRJV`، `gen-1790940171-6xSXeyo5lzOKpxtxO9EG`.
- نشت اطلاعات (برای مسئله ۴): هدرها `x-litellm-model-api-base: https://openrouter.ai/api/v1`، `x-litellm-version`، `x-litellm-key-spend` را به مشتری می‌دهند.
- **تأثیر بر داکیومنت:** بخش «قیمت‌گذاری» نهایی نشود تا A و B و منبع عدد پنل روشن شود.

**نتیجه‌ی تست ۴ (قطعی؛ پنل قبل/بعد + لاگ LiteLLM، درخواست ۵۴٬۰۲۲ توکنی × ۲ روی chat):**
- پنل مشتری (arefeh): قبل ۵۶ درخواست / ۵۷۵٬۲۰۲ توکن / ۰.۴۱$ ← بعد ۵۸ درخواست / ۶۸۳٬۲۴۶ توکن / ۰.۷۷$.
- افزایش: ۲ درخواست، ۱۰۸٬۰۴۴ توکن (= ۲×۵۴٬۰۲۲ دقیقاً)، ≈۰.۳۶$. مجموع هزینه‌ی لاگ LiteLLM: ۰.۳۳۷۷۲۰ + ۰.۰۲۷۱۷۴ = ۰.۳۶۴۹ ← **پنل هزینه را از لاگ LiteLLM می‌گیرد، نه قیمت × توکن** (آن ≈۰.۶۲ می‌شد).
- **اصلاح نتیجه‌ی تست ۳:** هزینه‌ی ثبت‌شده در لاگ برای `/v1/messages` هم cache-aware است (۰.۰۸۴۸۷ و ۰.۰۰۷۱۷۴، یعنی مثل chat) و هدر `x-litellm-response-cost-original` (۰.۰۷۸) **گمراه‌کننده** است، نه مبلغ واقعی. پس «بیش‌حساب ۱۰ برابری در `/messages`» (مشکل A) **رد شد**. فقط خود هدر در آن مسیر عدد دیگری نشان می‌دهد (cosmetic، اما مشتری ممکن است به آن تکیه کند).
- **شمارش توکن:** ستون «توکن‌ها» در پنل = prompt (شامل cache) + completion، بدون تفکیک. با کنسول Anthropic/Bedrock که `input_tokens` را جدا از cache نشان می‌دهد نمی‌خواند ← محتمل‌ترین منشأ شکایت پاتوق (نمایش، نه مبلغ). اقدام: تفکیک ورودی / cache خوانده / cache نوشته / خروجی در پنل.
- **مارجین:** هزینه‌ی ثبت‌شده در لاگ تا رقم ششم برابر `usage.cost` اوپن‌روتر است (مثلاً ۰.۰۰۷۱۹۹) ← **مارجین ۱۵٪ در هزینه‌ی صورت‌حساب دیده نمی‌شود.** ⚠️ بک‌اند/مالی: مارجین جای دیگری اعمال می‌شود یا نه؟ قیمت نمایش‌داده‌شده در صفحه‌ی مدل‌ها (با مارجین) با آنچه واقعاً کم می‌شود می‌خواند؟ (فقط برای مسیر OpenRouter دیده شد.)
- ⚠️ *هنوز انجام نشده:* همین تست با مدل OpenAI مستقیم (`gpt-5-nano`)؛ آنجا `usage.cost` از بالادست نیست و LiteLLM از قیمت ثبت‌شده‌ی خودش حساب می‌کند، پس cache فقط وقتی درست است که قیمت cache در تعریف مدل تنظیم شده باشد.

**نتیجه‌ی احتمالی و اقدام:**
- پنل هزینه را از LiteLLM می‌خواند و تخفیف cache درست است ← فقط برای مشتری توضیح دهیم «توکن cache هم شمرده می‌شود ولی ارزان‌تر حساب می‌شود»، و در پنل توکن را به ورودی، cache و خروجی تفکیک کنیم.
- هزینه با فرمول خودمان حساب می‌شود یا قیمت cache تنظیم نشده ← **اصلاح فوری** و در صورت بیش‌حساب بودن، تسویه با مشتریان.

## ۲. Claude Code با مدل‌های OpenAI مستقیم

- خطا: `400 Unknown parameter: 'output_config'` (قبلش `context_management`). Claude Code فیلدهای مخصوص Anthropic می‌فرستد.
- مدل‌های OpenRouter (مثل `bytedance-seed/seed-1.6-flash`) این فیلدها را می‌پذیرند و بی‌صدا حذف می‌کنند؛ مدل‌های OpenAI مستقیم (مثل `openai/gpt-5-nano`) ردشان می‌کنند.
- `drop_params: true` فقط پارامترهای شناخته‌شده‌ی OpenAI را حذف می‌کند. برای فیلدهای ناشناخته احتمالاً `additional_drop_params: ["output_config","context_management"]` لازم است. ⚠️ *کیارش تأیید کند.*
- نگرانی کیارش درست است: `drop_params` سراسری ممکن است پارامترهای مهم مشتری (مثلاً `tools`، `response_format`) را بی‌صدا حذف کند. حذف فقط فیلدهای مشخص امن‌تر است.
- نمونه‌ی تکرار در `docs-tools` / پیام تیم موجود است.
